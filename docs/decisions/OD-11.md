# OD-11 — Technology stack and hosting

**Status:** CLOSED
**Owner:** Engineering
**Needed by:** Phase 0 (blocking)
**Blocks:** Repo layout, ORM choice, queue, deploy target

## Question

What stack, and where does it run?

## Answer

**Stack:** FastAPI (Python) · PostgreSQL 16 · Redis 7 · SQLAlchemy 2.0 async ·
Alembic · Pydantic v2 · Next.js (React) · Server-sent events for realtime.

**Hosting:** any Postgres 15+ with managed Redis works. The app is a stateless
container behind a load balancer; the only stateful components are Postgres and Redis.

## Why these

- **PostgreSQL** is not a preference — the tenant isolation guarantee is built on its
  Row Level Security. `current_setting('app.business_id')` inside a policy is the
  mechanism that makes cross-tenant access impossible even if the ORM guard is
  bypassed. This is the single most load-bearing dependency in the system.
- **Redis** carries the queue, the SSE fan-out and the rate limiter. It is not the
  source of truth for anything; losing it loses queued work, not data.
- **SSE over WebSockets.** The realtime channel is server→client only, plus the
  occasional client→server form post. SSE reconnects on its own, works through
  corporate proxies, and needs no separate connection layer.
- **SQLAlchemy async** because every request path is I/O-bound against Postgres, and
  the ORM-level tenant filter (`do_orm_execute`) is the natural place to enforce
  isolation in the application layer as well.

## Deployment consequence

The app connects as `xenovarients_app` — `NOSUPERUSER NOBYPASSRLS`. Migrations run as
a separate owner role. If these two are the same role, RLS stops applying and the
isolation guarantee is silently gone.
