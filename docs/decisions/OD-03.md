# OD-03 — Tenant model

**Status:** CLOSED
**Owner:** Product
**Needed by:** Phase 1
**Blocks:** Data model, security model

## Question

Multi-tenant SaaS or a single business?

## Answer

**Multi-tenant SaaS on a shared schema**, with a `business_id` discriminator on every
tenant-scoped table and PostgreSQL Row Level Security as defence in depth.

## Why

The product is sold per business and the data model already hangs every record off
`business_id`. A shared schema keeps one migration path and one connection pool;
separate schemas or databases multiply both.

## How the guarantee is made real

Two independent layers, deliberately:

1. **ORM layer** — `db/tenant.py` installs a `do_orm_execute` hook that appends
   `business_id = :bid` to every SELECT/UPDATE/DELETE against a tenant-scoped model,
   and raises `TenantScopeError` when no tenant is in context. It gives a good error
   message.
2. **Postgres layer** — RLS policies keyed on the `app.business_id` session variable,
   with `FORCE ROW LEVEL SECURITY`. This catches anything that bypasses the ORM: raw
   SQL, a migration, a `psql` session. It gives the actual guarantee.

The layers cannot drift apart because `bind_tenant()` sets both at once, and
`clear_tenant()` runs on every session teardown so a pooled connection cannot leak a
tenant into the next request.

## Critical detail

The application connects as `xenovarients_app` — `NOSUPERUSER NOBYPASSRLS`, not a table
owner. Migrations run as a separate owner role (`migration_database_url`) because DDL
needs rights the app role must not have. If the app connected as a superuser the RLS
policies would be decorative, and the isolation tests would pass against empty result
sets while proving nothing.
