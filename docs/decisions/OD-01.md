# OD-01 — Customer, order and inventory data source

**Status:** OPEN — build proceeds behind an adapter interface
**Owner:** Product + Engineering
**Needed by:** Phase 0 (blocking)
**Blocks:** All of M1 Customer Genome, restock detection

## Question

Where do customer, order and inventory records come from, and how does this app read them?

## Why it matters

Every M1 feature reads from this source. The adapter interface, the schema of ingested
records and the restock detection loop all depend on the answer. If inventory is not
variant-level, RP-03 ("variants are never mixed") cannot be honoured and the requirement
has to be escalated, not silently relaxed.

## Options considered

| Option | Read access | Incremental sync | Inventory granularity | Effort |
|---|---|---|---|---|
| A. Read API on the source system | HTTP/JSON | cursor or `updated_since` | product or variant | Low, if the API exists |
| B. Direct database access | SQL | `updated_at` cursor | variant | Medium; coupling to their schema |
| C. CSV / Excel export over SFTP | File | full file, or a delta file | product | Medium; needs a scheduled import |
| D. Shopify-style webhook feed | Push | event-driven | product | Low, but not authoritative |

## Applied default

**Option A**, behind a `SourceAdapter` protocol (Phase 3 task 3.1). The adapter is the
only place that knows the source's shape; everything above it reads normalised rows.

The stub adapter ships with seeded fixtures so the whole of M1 is buildable and testable
without the real source.

## Investigation still required

1. Does a read API exist? If so: is incremental sync supported, and by what cursor?
2. Does the source carry a delivery-confirmation field, or only order status?
3. Is inventory tracked per variant, or only per product?
4. Does the source expose a stable customer id, or must identity be derived from
   phone/email? (Bears on CG-03 and on the identity ladder.)
5. If there is no API: what is the export cadence, and can we get a delta file?

## Fallback if it fails

Build the adapter against a CSV/SFTP export and a scheduled import job instead. The
adapter interface does not change — only the implementation behind it.

**Escalation trigger:** if inventory is not variant-level, RP-03 cannot be honoured.
Raise it with the owner rather than shipping a restock message that names the wrong
variant.
