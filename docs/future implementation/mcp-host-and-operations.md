# Add MCP hosting to XenoDesk

This plan starts with the existing read-only servers. The first milestone is one production code path where Agent Workspace calls a real MCP tool, returns verified data and records the outcome. The [submission answers](../MCP_SUBMISSION_ANSWERS.md) describe today's implementation.

## 1. Connect Agent Workspace to one server

1. In [core/config.py](../../backend/xenovarients/core/config.py), add an opt-in flag, an operator-controlled MCP base URL and a short overall call deadline. Document them in [backend/.env.example](../../backend/.env.example). Keep the integration disabled by default. Configure exact endpoint URLs under `/mcp/<name>/`, including the trailing slash. Do not take URLs from chat or tool inputs.
2. Add a small client module in `backend/xenovarients/platform/mcp/` using the project's pinned Python SDK. Confirm the installed SDK's client and transport signatures before wiring headers and timeouts. Use a request-scoped HTTP client/session with `Authorization: Bearer …` and the server-verified `X-Business-Id`. Keep per-user credentials out of shared client state, logs, and model input. The same [API principal resolver](../../backend/xenovarients/api/deps.py) validates membership and roles on the tool side. If the chat request cannot supply authenticated credentials, stop the MCP branch with an explicit response. [SDK transport documentation](https://github.com/modelcontextprotocol/python-sdk/blob/main/docs/client/transports.md)
3. In [api/workspace.py](../../backend/xenovarients/api/workspace.py), preserve the current FAQ, blocked-intent and active-ads-count paths. Add one explicitly selected read intent such as a restock preview, using `restock.preview_batch` after validating its arguments against the server schema. Allowlist server/tool pairs in the backend. Use SDK discovery for compatibility checks and call only tools the product explicitly supports. Return minimal structured facts with references. Surface refusals and unavailable data in the data route and preserve normal chat behavior when disabled.
4. For remote HTTP, use TLS and restrict the route to intended hosts and origins at the trusted proxy or application boundary. Review this before external exposure because [the existing mounts](../../backend/xenovarients/platform/mcp/app.py) disable SDK DNS-rebinding protection. If desktop hosting is required, smoke-test a named client's header handling and authorization against a development tenant before listing it on the form. For stdio, launch `python -m xenovarients.platform.mcp.faq_server` using the backend interpreter, keep protocol messages on stdout, and inject `XENODESK_BUSINESS_ID` and least-privilege database credentials from trusted configuration. Use a separate trusted process per configured tenant. Keep the in-product FAQ fast path local.

## 2. Add operational controls

- Apply a Redis-backed quota after HTTP tool authentication, keyed by business and caller with an MCP-specific namespace. Reuse the Redis infrastructure behind [the outbound limiter](../../backend/xenovarients/platform/ratelimit.py). Define separate MCP limits, an explicit rate-limit result and an explicit Redis-outage policy. Add an edge request cap for pre-auth traffic and a deadline for external sourcing calls.
- Record request ID, server, tool, duration and outcome in structured logs. Extend the existing `AiUsageEvent.tools_invoked` tracking for Workspace calls. Keep customer identifiers, raw arguments, tool results and credentials out of logs. Track success, refusal, quota exhaustion and timeout counts, and retain existing server health probes.
- Add a CI job with `pip install -e ".[dev,mcp]"` and run [the MCP unit tests](../../backend/tests/unit/test_mcp_servers.py). The current [workflow](../../.github/workflows/ci.yml) installs only the dev extra while the MCP tests import the SDK unconditionally. Also exercise the core API without the MCP extra and define how that job excludes optional MCP tests.

## 3. Expand only where the workflow needs it

- Start with deterministic routing to a few allowlisted tools. If model-selected tool use becomes necessary, add a bounded select → validate → execute → summarize loop around the [current Ollama client](../../backend/xenovarients/platform/llm/client.py). Treat tool output as untrusted data and keep writes on the existing owner-confirmed API path. The present worker already handles scheduled jobs. A separate agent framework or multi-agent coordinator is unnecessary for the first milestone.
- Use the [existing third-party ideas](future-mcp-plan.md) as candidates. Pilot one verified data provider through a separate allowlisted client configuration, for example a sourcing demand provider that receives only the required keyword and region. Use provider-specific credentials. Keep XenoDesk bearer tokens and customer data inside XenoDesk. A messaging integration may expose delivery status to chat. Any actual send stays with the confirmed outbound API. An analytics tool may prepare a preview in chat, with an explicit authenticated workflow handling external export.
- Keep legacy SSE and WebSocket unchecked in the form. If a real client requires another transport, validate its supported protocol and auth first, then add a distinct compatibility test and document the deployed route.

## 4. Additional open-source integrations

| Candidate | Where it fits | Implementation and acceptance check |
|---|---|---|
| OpenTelemetry | FastAPI app factory, Workspace MCP client, and HTTP tool handlers | Add opt-in FastAPI and SDK instrumentation. Export traces over OTLP to a collector. Add spans around each Workspace tool invocation and its handler using server, tool, duration, and outcome. Verify one test request is traceable end to end and that tokens, customer data, and tool payloads never appear in exported telemetry. [FastAPI instrumentation](https://opentelemetry-python-contrib.readthedocs.io/en/latest/instrumentation/fastapi/fastapi.html) |
| Qdrant | Existing optional Compose profile and `VectorStore` interface in [platform/vector/store.py](../../backend/xenovarients/platform/vector/store.py) | Add a Qdrant adapter behind configuration and keep pgvector as the default. Extend the embedding indexing path to populate the collection with document or chunk IDs and a tenant field. Require a server-derived tenant filter on every query. Benchmark recall and latency against pgvector and test isolation with two seeded businesses before enabling the adapter. [Qdrant multitenancy](https://qdrant.tech/documentation/tutorials/multiple-partitions/) |
| LangGraph | Optional orchestration behind the existing [Workspace chat handler](../../backend/xenovarients/api/workspace.py) | Pilot only when a workflow needs resumable, multi-step execution. Start with a sourcing research flow that gathers allowlisted read-only evidence and summarizes it. Scope checkpoints to the verified business, caller, and chat session. Verify that interrupted runs can resume within the tool-call budget and cannot resume from another business's session. [LangGraph durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution) |

Start with OpenTelemetry alongside the first Workspace MCP call. Evaluate Qdrant when retrieval benchmarks justify a second backend. Evaluate LangGraph when a workflow needs reliable pause and resume.

For the current build's submission, additional verified options are PyJWT for access tokens, argon2-cffi for password hashing, cryptography/Fernet for Meta Ads credential encryption, and pytest, pytest-asyncio, and Ruff for the test and lint workflow. The candidates above belong in future plans until their product integrations pass the acceptance checks.

## Acceptance checks

- With MCP enabled, an authorized Workspace request discovers and calls the selected tool against a seeded tenant. Chat returns sourced data and the tool name appears in usage records.
- Missing, revoked and wrong-tenant credentials or insufficient roles never return protected results. A second tenant's data stays isolated and preview calls leave records unchanged.
- Timeout and rate-limit paths produce explicit outcomes and avoid retry storms. Credentials and customer data stay out of telemetry.
- With the feature disabled or the SDK absent, normal chat, FAQ matching and approved write workflows still work. Verify the stdio FAQ with an actual client before naming that host as used.
